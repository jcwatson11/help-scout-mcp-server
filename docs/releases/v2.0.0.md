# Help Scout MCP Server v2.0.0

## Release Positioning

v2.0.0 replaces the wide tool surface with a three-tool gateway. The server now
advertises `search_help_scout`, `describe_help_scout`, and `read_help_scout`, and
routes every Help Scout read through them.

This is the read parity release. v1.9.0 was prepared but never published; its
scope ships here. No write tools are included.

The version is major because the advertised tool surface changed and because
names retired in the consolidation no longer resolve.

## Highlights

### Three Advertised Tools

- `search_help_scout` takes a plain-language intent and returns matching
  operation names and descriptions. Query terms are expanded across support
  synonyms, so "tickets" finds conversation operations.
- `describe_help_scout` returns full input schemas for up to ten named
  operations.
- `read_help_scout` executes one named operation. Unknown names come back with
  suggestions rather than a bare failure.

The gateway lives in `src/tools/gateway.ts`. Operation definitions and handlers
stay in `src/tools/index.ts`.

### 55-Operation Read Parity

The registry behind the gateway covers the current Help Scout Mailbox and Docs
read surfaces: conversations and threads, original source, attachments, inboxes
and inbox metadata, saved replies, customers and contacts, organizations,
customer and organization properties, tags, users, teams, workflows, webhooks,
satisfaction ratings, the seven report categories, and the Docs API.

Every operation is read-only and annotated as such.

### Page-Number Pagination

Collection operations use page-number pagination. Cursor parameters are gone from
the shared collection envelope. The one remaining cursor is the v3 Customers
path (`listCustomers` with `useV3` or a `cursor`, and `searchCustomersByEmail`),
where cursor pagination is upstream Help Scout behavior rather than a server
choice.

### Redaction Framing

`REDACT_MESSAGE_CONTENT=true` hides message bodies in responses. It is documented
as a context-saver: it keeps large message bodies out of the host's context
window. It is not a PII control and not a compliance boundary. Identifiers,
addresses, and metadata still flow through.

### Dependencies

`npm audit` reports zero vulnerabilities at release.

## Breaking Changes

Clients that call Help Scout tools by name are affected.

Names still in the registry continue to dispatch directly, so calls like
`getConversation` keep working as a compatibility path. Names retired in the
consolidation do not dispatch; they return a tool error pointing at
`search_help_scout`.

### Migration

| Removed name | Replacement |
| --- | --- |
| `searchInboxes` | `listAllInboxes` with `nameContains` |
| `advancedConversationSearch`, `comprehensiveConversationSearch`, `structuredConversationFilter` | `searchConversations` convenience filters |
| `getConversationV3` | `getConversation` with `includeSystemActors: true` |
| `getThreadsV3` | `getThreads` with `includeSystemActors: true` |
| `getOriginalSourceRfc822` | `getOriginalSource` with `format: "rfc822"` |
| `listCustomersV3` | `listCustomers` with `useV3: true` or a `cursor` |
| `getCustomerAddress`, `listCustomerEmails`, `listCustomerPhones`, `listCustomerChats`, `listCustomerSocialProfiles`, `listCustomerWebsites` | `getCustomerContacts` |
| `listSystemUsers` | `listUsers` with `includeSystemActors: true` |
| `getSystemUser` | `getUser` with `includeSystemActors: true` |
| `listUserStatuses` | `listUsers` with `includeStatuses: true` |
| `getUserStatus` | `getUser` with `includeStatus: true` |
| `listInboxCustomFields`, `listInboxFolders`, `getInboxRouting` | `getInbox` with `include: ["fields", "folders", "routing"]` |
| `getDocsSiteRestrictions` | `getDocsSite` with `includeRestrictions: true` |
| 32 individual report tools | `getCompanyReport`, `getConversationsReport`, `getProductivityReport`, `getUserReport`, `getHappinessReport`, `getChannelReport`, `getDocsReport`, selecting a sub-report through `report` or `channel` |

No capability was dropped. Each retired name is reachable through a parameter on
its parent operation.

The simplest migration is to stop naming operations at all: call
`search_help_scout`, then `describe_help_scout`, then `read_help_scout`.

## Compatibility

- OAuth2 credentials are unchanged: `HELPSCOUT_APP_ID` and
  `HELPSCOUT_APP_SECRET`.
- `HELPSCOUT_DOCS_API_KEY` is optional and only required for Docs operations.
- Full read coverage needs Read scopes beyond Mailboxes and Conversations.
  Reports, users, and tags each need their own scope.
- Results still return `structuredContent` plus a serialized JSON text block, so
  clients that parse `content[].text` keep working.
- The navigator plugin pins `help-scout-mcp-server@2.0.0`.

## Publish Sequence

Publishing is manual apart from the Docker build.

1. Merge the `dev` release-prep PR into `main`.
2. Tag `v2.0.0` on `main` from the merge commit and push the tag. The tag push
   triggers the Docker build and push.
3. Publish to npm by hand: `npm publish --otp=<2FA_CODE>`. There is no CI publish
   step.
4. Build the desktop bundle with `npm run mcpb:pack` and attach
   `help-scout-mcp-server-2.0.0.mcpb` to the GitHub release.
5. Create the GitHub release from the `v2.0.0` tag with these notes and the
   `.mcpb` attached.
6. After npm publish succeeds, bump the navigator plugin pin to
   `help-scout-mcp-server@2.0.0` and commit. Pinning before publish points users
   at a version npm cannot serve.
7. Verify public install paths:
   - `npx -y help-scout-mcp-server@2.0.0`
   - navigator plugin install
   - `.mcpb` install
   - `drewburchfield/help-scout-mcp-server:2.0.0`
8. Sync `main` back to `dev`.

## Verifying The Install

A connected client should list exactly three tools. If it lists more, or lists
none, the client is running a cached older build.
